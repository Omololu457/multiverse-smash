STAGE 3 — SMOOTHER CAMERA EASING (neutral <-> hit-confirm)        [DONE]
────────────────────────────────────────────────────────────────────────
File: camera.js — the shared advance() interpolation used by BOTH the
neutral two-fighter framing (update/updateMulti) AND every hit-confirm/
special/domain focus (focusBetween/focusOnFighter → advance). One place,
so the change is global and consistent.

FINDING (verification part): the transition was NOT a hard cut and NOT a
fixed-duration linear tween. It already used lerp(current, target, smooth)
= an exponential EASE-OUT toward the target. So the settle was already
eased. The one rough spot was the per-frame RATE LIMIT: the old code hard-
clamped the step to a fixed ceiling —
    nextZoom = zoom + clamp(lerpStep, -zoomStep, zoomStep)     // hard cap
    nx       = x    + clamp(lerpStep, -maxPanStep, maxPanStep) // hard cap
For any transition big enough that the lerp step exceeded the ceiling, the
camera ran at a CONSTANT max rate (a linear segment) and then abruptly
handed off to the ease-out — a visible "kink"/snap on larger reframes.

CHANGE (contained — the interpolation function only): replaced the hard
clamp with a SOFT, eased rate-limit:
    function softStep(delta, cap) { return cap>0 ? cap*Math.tanh(delta/cap) : delta }
    nextZoom = zoom + softStep(lerpStep, zoomStep)
    nx       = x    + softStep(lerpStep, maxPanStep)   // same for ny
tanh(x) ≈ x for small steps, so the small neutral↔hit-confirm zoom changes
keep the existing ease-out almost exactly; it saturates to ±cap for big
steps, so a large reframe now ACCELERATES smoothly into the ceiling and
DECELERATES out of it — the linear kink is gone. |tanh| < 1 guarantees the
step never exceeds `cap`, so the original anti-pop/anti-jerk safety is kept
(actually slightly tighter). Deterministic — no RNG, no new state.

Numeric proof (cap = zoomStep = 0.02):
    delta 0.001 → hard 0.0010 / soft 0.0010   (hit-confirm: unchanged)
    delta 0.008 → hard 0.0080 / soft 0.0076   (near-cap: gently eased)
    delta 0.020 → hard 0.0200 / soft 0.0152   (kink region: smoothed)
    delta 0.050 → hard 0.0200 / soft 0.0197   (large: same ceiling)
    delta 0.200 → hard 0.0200 / soft 0.0200   (huge: same ceiling)
    every soft step strictly within ±cap.

The deliberate one-shot SNAPS (giant-form first-frame reveal in update(),
match-start snap in updateMulti) are untouched — those set zoom/x/y
directly and never route through the softened step, exactly as before.

  Math.random for shake) so it cannot affect sim determinism by construction;

3.1  IS THERE A "KILLING BLOW" HOOK TO BUILD ON? — PARTIALLY.
  • KO interception EXISTS: `_checkMatchOver()` (game.js ~3978) already
    intercepts match-over and calls `_tryStartBrutality(winner)` (~4333:
    `if (!_tryStartBrutality(winner)) _enterVictoryScreen()`). Round-end
    flows through `checkRoundEnd`. So the place to hang a Brutality is
    already there and already used.
  • BUT the existing trigger is WINNER-based, not MOVE-based: it fires when
    the loser's health ≤ 0 on a KO (never on a time-over), gated by an
    eligibility set. It does NOT know WHICH move landed the killing blow.
  • MISSING PIECE for the user's move-tied design: nothing currently stamps
    "this specific special/ultimate emptied the bar." The engine DOES know
    `fighter.currentMove` / `currentAttack.name` live at damage time
    (combat.js). So the new work is small + localized: in the damage-apply
    path, when the defender's HP crosses to ≤0, stamp
    `attacker._killingBlowMove = <move id>`; `_tryStartBrutality` then reads
    it to pick the per-move finisher (or fall back to "The Classic").
    → This is the core new engineering for Brutalities. Low-risk, one hook.

WHAT CHANGED (the design, as shipped)
--------------------------------------------------------------------------
Replaced the mirror-decoy clone behavior for the 6 listed characters with a
summon+assist system. A clone now SPAWNS and STANDS STILL (no movement-
mirroring, no position-following — the behavior the user rejected is gone
for these 6). A dedicated assist key drives three on-demand actions, each
on its OWN cooldown (a managed resource, not spam):

  KEY BINDINGS (real keyboard, Player 1):
    ","        = spawn a clone      (unchanged)
    "."        = disperse clones    (unchanged)
    "h"        = ASSIST + Neutral   → SUMMON strike (NEW)
    Fwd + "h"  = ASSIST + Forward   → AMBUSH rush   (NEW; forward = toward foe)
    Back + "h" = ASSIST + Back      → SWAP / per-char back-action (NEW)
    "/"        = legacy swap        (kept as an alias; still works)
  "h" was chosen because input.js showed it FREE (P1 uses a/d/w/s, j/k/i/l/u,
  o/p/;, and , . /) and it is ergonomic to tap while holding a/d.

  ACTION TYPES (MK1 Summon/Ambush split):
    • SUMMON (Neutral): the player briefly FREEZES (hitstop) while a clone
      lunges in front of the opponent and strikes with a launcher — a combo-
      extender. Consumes one standing clone.
    • AMBUSH (Forward): a clone rushes in from where it stood, IMMEDIATELY,
      regardless of what the player is doing — usable mid-combo (punish tool),
      no player freeze. Consumes one standing clone.
    • BACK: per-character (see below).

  COOLDOWNS (frames @60fps, in cloneAssist.js CLONE_ASSIST_CD):
    summon = 180 (3.0s) · ambush = 150 (2.5s) · swap/back = 120 (2.0s)

  naruto   — SWAP (substitution: trade places with a clone; clone kept as decoy)

  itachi   — SWAP, PLUS Crow-Clone flavor that applies to ALL his clone loss:

             apply the `obscured` debuff to the opponent (a dark crow-feather
             veil, ~1.5s), made visible by a new drawCrowBlindOverlay.
