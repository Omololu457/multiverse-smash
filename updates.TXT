T2a  ZARAKI non-sheet 404 ................................ FIXED (real 404)
  Root cause: sound.js DRAGON_BALL_TRANSFORM_SFX = "dragon_ball_transformation.mp3"
  — a file that was never added to the repo. playDragonBallTransformSfx() loaded
  it with a null fallback, so it 404'd with no procedural degrade; zaraki's Shikai
  cinematic routes through it, tripping the suite's no-404/no-console-error check.
  Fix: a procedural `transformation` cue already exists (sound.js ~line 254,
  "generic/shared transformation cue") — the mp3 was a dead override of it. Routed
  playDragonBallTransformSfx() to this.play(SFX.TRANSFORMATION) and removed the
  dead file constant. No missing asset referenced -> no 404.
  VERIFY: test:zaraki 82/0 x 3 runs (was tripping "no JS/console errors").

T2b  GHOSTFACE variant-key collision .................... FIXED (real collision)
  Root cause: "ghostface_billy" is in BOTH the 12-key variant template
  (GHOSTFACE_VARIANT_KEYS) AND the live roster — Billy was intentionally PROMOTED
  to a standalone char (bespoke Special/Ultimate gated on rosterKey, NOT the
  variant template; isGhostfaceVariant is not wired into any live combat path, so
  ZERO runtime conflict). The stale assertion assumed none of the 12 were live yet.
  Fix: the collision check now exempts intentionally-promoted variants (+ a new
  assertion that Billy IS registered live). The 12-key template is unchanged
  (Billy is canonically one of the 12; 5 other assertions require the count = 12).
  VERIFY: test:gf-variants 180/0 x 3 runs.

T2c  ISSHIKI flaky ground-string damage ................. TEST-ONLY (3 assertions)
  Root cause: fixed-frame harness taps raced the shared rekka cancel-on-hit latch
  AND let the dummy's knockback drift it out of range mid-string — so intermittently
  only the opener landed. The GAMEPLAY was correct (the air-string, which re-lifts
  every frame, always worked). Same class hit the Daikokuten cube-trap assertion
  (60-frame observation window ended before the first auto-tick, TICK_INTERVAL 36).
  Fix (harness only): pin the dummy in range between ground taps (mirrors the air
  re-lift), add horizontal pinning to the air re-lift too, and poll for the cube's
  first tick instead of a fixed window.
  VERIFY: test:isshiki 52/0 x 5 runs (was flaking 1-2/5 across 3 assertions).

T2d  ALT_SUKUNA flaky cleave rekka ...................... TEST-ONLY
  Root cause: same rekka class. The follow-up reuses the SAME Heavy button, so the
  opener's ~10-frame INPUT BUFFER kept `heavy` latched — the fixed-frame second tap
  either wasn't a fresh edge or landed outside cleave1's cancel window, so cleave2
  intermittently never fired (only cleave1's 33 dmg). Gameplay is correct.
  Fix (harness only): hold range, wait for the connect-latch, then let the input
  buffer fully clear (release gap) so the second Heavy is a genuine fresh EDGE
  inside cleave1's recovery window.
  VERIFY: test:alt-sukuna 21/0 x 5 runs (was ~1/4 pass; cleave2 now always fires, -90).

T3a  FRIEZA UP-ATTACK ................................... FIXED launch (claims = NON-ISSUE)
  The two SPECIFICALLY-CLAIMED bugs are non-issues, PROVEN LIVE:
    - "declared frame data != real timing" — FALSE. active=3/recovery=14 declared,
      applied verbatim by startMove (no _dur scaling at 1x). Measured identical.
    - "under-launches versus its own spec" — FALSE. Declared launchVy -30, measured
      peak p2.vy = -30. The engine applies it faithfully (exact-mode launcherAttack).
  The REAL gap: -30 is the frail/glass-cannon launch tier, mis-assigned to a
  mid-weight bruiser (HP 1100). Reference bruisers goku/vegeta launch at -32
  (measured). So Frieza under-launched vs its ARCHETYPE peers.
  Fix: frieza upAttack launchVy -30 -> -32 (characters.js). LIVE VERIFY: now measures
  -32, matching goku/vegeta.

T3b  COMEBACK FINISHER scales poorly vs tanky ........... FIXED (%-of-target)
  Diagnosis: it was already % of HP (round(min(USER.maxHP x 0.32, 360))) — but of
  the USER's own HP, hard-capped at 360. The flat cap shrank to a weak % of a tanky
  target's bar (360 = just 24.8% of Superman's 1450 vs 32% of a frail bar).
  Fix (combat.js): damage now = clamp(TARGET.maxHP x 0.32, dmgFloor 300, dmgCap 470)
  — a consistent slice of the OPPONENT's bar, scaled at commit (target locked).
  Floor/cap are guardrails only (roster 950->1450 maps to 304->464, both inside the
  band); they exist to prevent absurdity vs a hypothetical extreme-HP target.
  LIVE VERIFY (5/5): vs shinobu(960) lands 307; vs superman(1450) lands 464 —
  proportional (chunks MORE off the tanky target). Probe + real landed damage match.

T3c  METERLESS COMBO-BREAKER over-reward ................ FIXED (threshold +1)
  Diagnosis: trigger threshold is a single roster-wide COMBO_BREAKER.threshold = 3
  (i-frames = 24). Meterless detection is dynamic (traits.hasEnergy===false -> 8
  chars: zenitsu/rengoku/shinobu/inosuke/nezuko/maki/toji + baki). NOTE: the audit
  "specific recommended value" the prompt references does NOT exist in any repo doc
  (searched all .md/.TXT) — so I used the smallest meaningful bump.
  Fix (combat.js): meterless fighters now need ONE more combo hit to break —
  meterlessThreshold = 4 (meter chars unchanged at 3). i-frame window UNTOUCHED,
  mechanic UNTOUCHED. The game.js pre-gate (>=3, a cheap filter) still passes 4 through.
  LIVE VERIFY (3/3): shinobu no-longer-breaks at combo 3, breaks at 4; meter char
  (sasuke) still breaks at 3.
