TRACK B — DESKTOP / STANDALONE APP LAUNCHER   [FOUND, WORKS]
------------------------------------------------------------------------
COMMAND TO LAUNCH THE FULL-SCREEN STANDALONE APP (from project root):

        npm run desktop

  - Delegates to  npm --prefix electron start  -> runs electron/main.mjs.
  - Opens a native FULLSCREEN Electron window (Mac/Win/Linux).
  - Electron IS installed + configured (electron/ subfolder, electron
    ^33.4.11 as a devDependency; the binary is present). Isolated in its
    own package.json so the main project carries no Electron bloat.

HOW IT WORKS: the game is a pure static web app (ES modules + importmap).
Electron can't load ES modules over file:// (CORS), so main.mjs starts a
tiny localhost HTTP server (reusing tools/serve.mjs) and loads the game
from http://127.0.0.1:PORT - byte-identical to the browser build, zero
game-code changes. Adds durable save persistence + gamepad activation on
the cold title screen.

OTHER COMMANDS:
  npm run desktop:capture     -> headless screenshot to electron/shots/poc.png
  npm run desktop:diag        -> DIAG=1 verbose logging
  npm run verify:gamepad-gate -> controller detection on the home screen

STATUS: a working proof-of-concept (screenshots in electron/shots/ prove
live gameplay). NOT yet a packaged distributable (.dmg/.exe/.AppImage) -
that needs an electron-builder config + icon + code-signing, none of which
require game-code changes. For tomorrow's playtest, `npm run desktop` gives
the full-screen standalone experience right now.

TRACK C — RENDER LOOP / HIGH-REFRESH RE-VERIFICATION   [HEALTHY]
------------------------------------------------------------------------
HEADLINE: the render loop is solid after the new FX systems. No stutter
observed; the hot FX paths are allocation-pooled.

1) requestAnimationFrame IS driving rendering (game.js gameLoop). IMPORTANT
   NUANCE: the loop is INTENTIONALLY GATED to a fixed 60 Hz via a real-time
   accumulator - it does NOT run uncapped at the display's native refresh.
   This is BY DESIGN and CORRECT for this engine: physics, timers, cooldowns
   AND sprite-frame advancement all step exactly once per pass, so letting
   rAF run at 120/144/240 Hz would make the whole game run 2-4x too FAST
   (this was a real past bug - Toji jitter / too-fast intros). On a high-
   refresh monitor the game correctly stays at 60 fps game-speed; extra rAF
   callbacks are skipped. (So "sync to native refresh rate" is the wrong
   goal here - the 60 Hz lock is the fix, not a limitation.)

2) NO per-frame GC churn from the new visual systems. The hot paths are
   pooled (Stage 22C): damage numbers use poolAcquire("dmg")/poolRelease
   and O(n) compaction on expiry; hit sparks + brutality debris use
   poolAcquire("spark"). Confirmed in code.

3) LIVE MEASUREMENT (real match, headless Chromium, sampled real rAF
   intervals during a live BRUTALITY + continuous input, 226 frames):
        avg 16.67 ms - p50 16.70 ms (= exactly 60 Hz) - p95 17.60 ms -
        max 17.70 ms - DROPPED FRAMES (>33ms): 0
   The brutality (the most particle-heavy system) fired and captured its
   sprite while the frame line stayed flat. Zero JS errors.

HONEST LIMITATION: I could not make keyboard normals connect in the
headless harness to show a live NON-ZERO damage-number count, and the
direct hit-probe bypasses the FX bridge (FX are spawned in updateBattle,
not in combat.resolveAttackHit). So the damage-number stress is verified
by CODE (pooling) + the live brutality run, not by a live combo counter.

SELF-VERIFY ON YOUR REAL 120/144 Hz MONITOR TOMORROW:
   open the game with  ?debug=1  -> a live overlay shows
   "FPS ... frame Xms avg / Yms max" (stays green under ~20 ms) and
   "pool: N reused / M alloc" (allocs should stay near-flat during a big
   combo or brutality). If frame-max stays green during a brutality + long
   combo, you're clean. (Probe kept at harness/_perf_probe.mjs.)
