========================================================================
 SECTION 0 — THE DESIGN PHILOSOPHY (why we're doing this at all)
========================================================================
You said the thing that matters most: you want a HIGH SKILL GAP. Not more
characters that do more damage -- characters that reward a player who plans,
commits, and executes cleanly, and PUNISH one who doesn't. The single
sentence this whole doc is built around:

    "A great mechanic makes the player COMMIT to a plan, then makes the
     PAYOFF depend on their EXECUTION of that plan."

Your Naoya example is the perfect statement of this, so it's our north star:
Projection Sorcery divides a second into 24 frames -- you commit to a sequence
of movements, and if you can't reproduce all 24 cleanly, the technique fails
(and you're exposed). That is COMMITMENT + EXECUTION in one mechanic. The
skill isn't "press the strong button," it's "can you actually pull the whole
plan off under pressure."

Shadow clones are not the point. They're the best BASE to prototype this on,
because a clone is a physical object you place on the field in advance
(commitment) and then have to use correctly in a timed way (execution). If
we get the clone "commit -> execute -> punish-if-you-fail" loop feeling right,
that same skeleton drops onto Projection Sorcery, onto a charge-and-release
character, onto a resource-gambit character -- anything you want to add later
to widen the roster's skill ceiling. So this doc designs CLONES SPECIFICALLY
but with the GENERIC skill-expression frame underneath, called out where it
generalizes.

Three properties every mechanic in here is measured against:
  1. COMMITMENT  -- you spend/place something in ADVANCE and it's visible to
                    the opponent (a resource they can attack).
  2. EXECUTION   -- the payoff is a timed input sequence; sloppy input = weaker
                    or failed result, not a refund.
  3. COUNTERPLAY -- the opponent has a real, readable answer (attack the setup,
                    bait the sequence, block the right way). No unreactable
                    50/50s that just come down to a guess.

If an idea below fails one of those three, it's flagged. Cut those first.


========================================================================
 SECTION 1 — THE CORE FIX: "MAKE A CLONE A REAL GAME OBJECT"   [NEW]
========================================================================
This is your exact complaint: "it's almost like it's not a real game object
that you can interact with -- the shadow clones have been a real hit or miss."
You're right, and here's the concrete reason, plus the fix. EVERYTHING else
in this doc depends on this being solved first. It is Pillar A / Stage 1.

WHAT'S ACTUALLY WRONG (diagnosed in code)
-----------------------------------------
The game resolves hits in ONE place: resolveAttackHit(attacker, defender)
(combat.js:2685). That function only ever gets FIGHTERS handed to it. The
main battle loop (game.js ~1747) loops over the fighter list to decide who
got hit -- clones are in a SEPARATE list (activeSummons) that this loop never
looks at.

So today a clone does a fragile RETROACTIVE self-check inside its own update
(summons.js:1153): every frame it asks "is an enemy attack active right now,
AND overlapping me right now, AND am I in the idle state right now?" If any of
those three isn't true on that exact frame, the hit is missed. That's the
"hit or miss." And because the clone never goes through resolveAttackHit, when
it DOES register it skips everything real hits do: hitstun, knockback, block,
grab, juggle, combo scaling, counter-hit, hit-sparks, AI target selection.

A clone right now is a painted decoy that occasionally notices it was touched.
It is not a body.

THE FIX (make a clone a lightweight fighter-shaped target)   [KEEP?]
--------------------------------------------------------------------
Give a clone the small set of fields the hit system already expects on a
"defender," and register it in the loops that pick targets:

  (a) TAKING HITS: add clones to the target list the attacker's swing is
      tested against, so resolveAttackHit(attacker, CLONE) runs through the
      SAME path as hitting a fighter. The clone then legitimately eats the
      hitbox, plays a real hit reaction, and poofs -- no more self-check.
      Result: if your sword visibly overlaps a clone, it dies. Every time.

  (b) PROJECTILES: same idea -- clones join the projectile-vs-target pass
      instead of the bolt-on revealClonesHitByProjectiles step (summons.js:806).

  (c) BLOCK / GRAB / JUGGLE: because it now flows through resolveAttackHit, a
      clone can be made to block, be grabbed, or be juggled if we want it --
      we opt IN per behavior, we don't get it by accident.

  (d) AI: the opponent AI's target list includes clones as "cheap, one-hit,
      possibly-fake" threats, so the CPU respects them instead of walking
      through them. (This is also what makes clones feel real in 1P.)

DESIGN GUARDRAILS so this doesn't destabilize the mature engine:
  - A clone is still ONE-HIT-DIES by default. Making it a real target does
    NOT mean giving it a health bar. The hit lands through the real path,
    then we immediately route it to the poof lifecycle.
  - A clone must NEVER steal a hit that was meant for the real fighter on the
    same frame (priority: real fighter first, clones second). This keeps
    combos on the real target intact.
  - The chakra-split economy (summons.js:945) is untouched: destroyed clone =
    lost share; dispel = safe recall. That asymmetry is good, keep it.
  - Ship behind a test harness (harness/clone_realhit.test.mjs style) proving
    BEFORE=missed-hit / AFTER=guaranteed-hit, plus a determinism pass, before
    it's considered done. Same rigor as every other system.

WHY THIS IS THE RIGHT FIRST STEP: it's the thing you actually complained
about, it's invisible-but-foundational, and BOTH the barrage sequencing
(Section 2) and the consciousness-swap (Section 3) are unbuildable-feeling
until a clone is a body you can reliably hit and be hit by.


========================================================================
 SECTION 2 — PILLAR B: INPUT-SEQUENCED CLONE TECHNIQUES ("UZUMAKI BARRAGE")
========================================================================
This is the skill-expression heart of the clone system and the direct
answer to "a certain amount of button combos you have to press to get a
specific outcome, and if you miss a beat it can't be done."

THE GENERIC MECHANIC: a "COMMITMENT SEQUENCE"   [NEW] [KEEP?]
------------------------------------------------------------
A clone technique is not a single button. It is:

   REQUIREMENT  ->  a timed INPUT SEQUENCE  ->  each beat driven by a CLONE
                                             ->  miss a beat = the whole
                                                technique FAILS (whiff +
                                                recovery), not a refund.

This is the exact structure of your Naoya idea, just at a coarser grain
(beats instead of 24 frames). If you like how it feels here, we can later
tighten a character (Naoya) to the literal per-frame version.

Worked example -- U Z U M A K I   B A R R A G E  (Naruto):
  REQUIREMENT: at least 3 live clones on the field (you had to COMMIT to
               spawning and PROTECTING them first -- opponent could have
               popped them).
  ACTIVATION:  a starter input (e.g. down-forward + Heavy) that only ARMS
               the barrage if the requirement is met; otherwise it's a
               normal move / whiff (no wasted resource beyond the normal).
  THE SEQUENCE (each beat = a timed follow-up press, each assigned to a clone):
     Beat 1  -- UP attack  : one clone kicks the opponent airborne (launcher).
     Beat 2  -- the string only CONTINUES if beat 1 CONNECTED. Miss the up
                attack (whiff or they blocked/teched) -> the barrage ENDS here.
                The clones you committed are spent, you're in recovery. This
                is the punish for bad execution -- exactly what you described.
     Beat 3+ -- each subsequent clone adds a hit of the juggle on its own
                timed press; drop the timing and the last clones don't fire.
  PAYOFF: full clean execution = the iconic multi-clone air combo finisher.
          Partial execution = a weaker, shorter version. Failure = you're
          exposed. The damage LADDER rewards clean play, it doesn't gate
          the move behind an all-or-nothing 1-frame link.

WHY THIS FITS THE THREE PROPERTIES:
  - COMMITMENT: you needed 3 clones up first, in advance, on a field where
    the opponent could destroy them (now that Section 1 makes them hittable).
  - EXECUTION: it's a real timed sequence; missing the up-attack beat kills
    the string. Skill decides how much of the barrage you actually get.
  - COUNTERPLAY: opponent can pop your clones before you start, block the
    starter, or tech/air-escape the launcher to break the sequence at beat 2.

WHAT ALREADY EXISTS WE BUILD ON (so this is ~half-built, not from scratch):
  [EXISTS] "Clone Rendan Storm" (#21) -- a clone-count-gated light-string
           extension (game.js:2312). Promote/reshape this into the barrage.
  [EXISTS] consumeShadowClones(owner, n) -- spends N clones as a combo cost
           and returns their positions (summons.js:1051). This is exactly the
           "each beat is a clone" spender; the positions let each clone strike
           from where it stood.
  [NEW]    the SEQUENCER: an armed-technique state machine that tracks the
           current beat, checks connect/timing per beat, and fails the string
           on a missed beat. This is the real new code and the skill layer.

PER-CHARACTER SEQUENCES ("many combos with all the clones") -- see Section 6
for the full table. The sequencer is ONE system; each character just supplies
a different beat-list (Minato's beats teleport between clone marks, Itachi's
beats each breathe fire, etc.). That's how we get variety without N systems.

TWO INPUT-STRICTNESS OPTIONS FOR YOU TO PICK  [KEEP? -- choose one]
  (i)  LENIENT/LADDER (recommended to start): each beat has a generous timing
       window; missing one ends the string early but you keep what connected.
       Skill = how long a string you can maintain. Approachable, still deep.
  (ii) STRICT/ALL-OR-NOTHING: miss any beat and the ENTIRE technique fizzles
       with punish recovery (closest to the Naoya "or it doesn't work" feel).
       Higher ceiling, higher floor, more frustrating for new players.
  My rec: ship (i), and offer (ii) as a per-character "hard" signature for
  the 1-2 chars whose identity IS execution (Naruto's true Barrage; later
  Naoya). Don't make the whole roster all-or-nothing.


========================================================================
 SECTION 3 — PILLAR C: CONSCIOUSNESS-SWAP SUBSTITUTION   [NEW]
========================================================================
Your second scenario: "if I get hit and I want to replace myself with a
shadow clone... my consciousness kind of switches to a different Naruto clone
... I have to keep track of where I am because the clones don't look different
from the actual player." This is a MIND-GAME mechanic and it's fantastic for a
skill-gap game. It is DIFFERENT from what exists today -- be clear on that:

  [EXISTS] the current "Substitution Chain" (abilities.js:1960) = Block+Special
           while clones are up NO-SELLS an incoming hit (i-frames), spending a
           clone per use. It's a defensive get-off-me. It does NOT move you.
  [NEW]    CONSCIOUSNESS-SWAP = a POSITIONAL identity swap. You don't just
           tank the hit -- you and a chosen clone TRADE PLACES, so the body
           that "got hit" turns out to have been the fake, and the real you is
           now standing where a clone was. "That was never me."

HOW IT PLAYS  [KEEP?]
  - PRECONDITION: you have >=1 live clone (Section 1 makes them real bodies,
    which is WHY this now works -- you're swapping into an actual object).
  - INPUT: a dedicated swap input during a hit/whiff-punish window (distinct
    from the no-sell; or we fold both onto one input with the swap as the
    "hold a direction" variant -- your call).
  - RESULT: control instantly transfers to the clone at ITS position; the
    old body becomes a clone (or poofs, see options) at YOUR old position.
    Screen does NOT tell you which is which afterward -- you must have been
    tracking your clone placements. THAT is the skill: good players set up
    clones in smart spots precisely so the swap leaves them safe/advantaged.
  - SELF-TELL QUESTION (your explicit worry): do we give the CONTROLLING
    player any private marker on their real body?
       Option A -- TRUE BLIND (recommended for max skill gap): no tell, ever.
                   You track by memory + your own placement. Highest ceiling,
                   matches "I have to keep track of where I am."
       Option B -- FAINT PRIVATE TELL: a subtle marker only the controlling
                   player can see (opponent can't), e.g. a 1px reticle. Lowers
                   the ceiling but far more approachable. Could be a difficulty/
                   accessibility toggle rather than a global choice.
    My rec: build TRUE BLIND as the real mechanic, expose Option B as an
    accessibility/training toggle (we already have a clone-tell filter,
    summons.js:797, currently used for debug -- repurpose it here).

COUNTERPLAY (so it isn't a free escape):
  - It costs a clone (lossy, like a destroyed one -- spends the chakra share).
  - It has startup, so a true meaty / OS can still catch the swap.
  - The opponent CAN attack the clone you'd swap into; if they popped it, the
    swap has no destination and fails (whiff recovery). Commitment again.
  - Limited by clone count and the shared chakra pool -- you can't swap forever.

WHY IT'S GREAT FOR SKILL GAP: it turns clone PLACEMENT into a defensive
resource. Where you left your clones two seconds ago decides whether your
escape leaves you safe or in the corner. Positioning foresight = skill.


========================================================================
 SECTION 4 — HOW THE THREE PILLARS FIT TOGETHER
========================================================================
  Section 1 (real objects)  is the FOUNDATION -- do it first, alone, prove it.
  Section 2 (barrage)       is OFFENSE built on clones you protected.
  Section 3 (swap)          is DEFENSE built on clones you placed.
  Together they make a clone a single resource with an offensive AND a
  defensive expression, both gated by the SAME commitment (spawn + protect +
  place well). That coherence is what makes a mechanic feel deep instead of
  like three bolted-on gimmicks. A strong clone player is juggling: "do I
  spend these 3 clones on a Barrage for damage, or hold them as swap-escapes
  for defense?" That tension is the skill.

 SECTION 6 — PER-CHARACTER CLONE REPERTOIRE  (the "many combos" list)
========================================================================
One sequencer (Section 2), many beat-lists. Each char's clones already reuse
that char's REAL normals via CLONE_BODY_SETS[owner].attacks (summons.js:831) --
so "the clone throws the character's own moves" is already how it works; we're
adding SIGNATURE SEQUENCES on top. Each entry: [signature technique] =
requirement + the beat sequence. All [NEW] unless noted.

NARUTO  (volume / execution identity -- his clones are the swarm)
  - Uzumaki Barrage (Section 2 example): 3+ clones -> up-launcher beat -> juggle
    beats. His signature STRICT-option candidate (the "or it fails" version).
  - Uzumaki Naruto Combo (2000 Blows) [KEEP?]: 4 clones -> hold-sequence of
    rapid alternating light beats -> clones pile the opponent; a longer, more
    lenient ladder for the same fantasy at lower execution cost.
  - Clone Rendan Storm [EXISTS #21]: keep as the light-string entry point that
    the Barrage escalates out of.

MINATO  (precision / teleport identity -- few clones, placed exactly)
  - Flying Raijin Barrage: 2 clones placed on his kunai marks -> each beat
    TELEPORTS Minato to a clone's position and strikes, so the sequence is
    also a movement puzzle (you're deciding your own next position each beat).
    This is the most "skill-expression" of the clone sequences -- commit your
    marks, then execute a teleport route. Very high ceiling. Strong pick.

HASHIRAMA  (area control identity -- many clones, each plants terrain)
  - Deep Forest Barrage: clones each erupt a Mokuton tree on their beat
    (reuses his existing clone-tree special, summons.js beginCloneSwing) -- the
    sequence LAYS the battlefield rather than juggling one target. Zoning skill
    instead of combo skill. Nice contrast to Naruto.

TOBIRAMA  (technician identity -- water clones + body-flicker)
  - Water Clone Flicker String: clones are water; each beat body-flickers him
    to a clone and leaves a water-slash. Reuses his Water Flicker escape art.
    Plays like a defensive-offense hybrid; leans on his speed stat.

BORUTO  (modern hybrid -- small clone count, tool-assisted)  [near-free add]
  - Clone + Rasengan setup: 1-2 clones help form a bigger Rasengan on a timed
    beat (canonical "clone helps shape the Rasengan"). Low clone count, high
    reward on clean input. Uses existing boruto clone art + Rasengan special.

KAKASHI  (copy-ninja -- clones as feints, not swarm)
  - Clone Feint -> Raikiri: 1 clone; the sequence is a MIXUP not a juggle -- the
    clone commits to one approach while the real Kakashi sets up Raikiri from
    another angle. Skill = selling the fake. Fewer beats, more mind-game.

ITACHI (optional) -- Clone Fire-Flower: each clone breathes Great Fireball on
  its beat (reuses fireballCast); a zoning barrage. Great toy, defensible lore.

HIRUZEN (optional) -- generic "Shadow Clone Combo"; flavor only, no signature.

MADARA (optional, [LORE?]) -- Wood Clone spikes; mirror of Hashirama, weakest
  identity case. Only if you want the number-of-chars, not for flavor.

NOTE on your "Sasuke multiple fireball / Mito flying-raijin" line: those are
GREAT instincts but they're really "clone-assisted MULTI-JUTSU," which is

 SECTION 7 — BEYOND CLONES: THE SKILL-GAP ROADMAP  (roster diversification)
========================================================================
You said clones were "just a good base" and the real goal is diversifying the
roster with high-skill-ceiling mechanics. Here are candidate NON-clone
mechanics that reuse the SAME "commitment sequence" skeleton (Section 2), so
building the clone sequencer first pays off across all of them. These are
SEEDS for later -- flagged so you can earmark, not build now.

  [SEED] NAOYA -- PROJECTION SORCERY (your favorite): the literal 24-frame
      version of the commitment sequence. Touch the opponent to "tag" them,
      then you must input a clean movement sequence within a tight window; land
      it and they're frozen for a beat (canonical "can't reproduce 24 frames =
      frozen"). This is the sequencer at its STRICTEST grain. Perfect capstone
      once the lenient clone version proves the feel. You said you'll add this
      later -- the clone sequencer is literally the prototype for it.

  [SEED] A CHARGE-COMMIT character: banks "stocks" over time that decay if
      unused; big payoff only if you spend them in a specific order. Commitment
      = the visible stock bar the opponent races; execution = the spend order.

  [SEED] A RESOURCE-GAMBIT character (e.g. an Orochimaru rework): sacrifices
      own HP to arm a technique that must then be "cashed" by a sequence;
      whiff the cash-in and the HP is just gone. High risk/reward, on-brand
      for a character who experiments on himself.

  [SEED] A KAMUI/PHASE character (Obito): commit to a phase-out with a fixed
      duration; you must re-enter with the right timing to convert -- mistime
      and you re-materialize into a punish. Movement-based execution skill.

  [SEED] A COUNTER-READ character: a parry whose reward scales with how
      SPECIFICALLY you called the incoming move (light vs heavy vs grab),
      layering onto the existing high/low classifier (combat.js:236).

Common thread: NONE of these is "more damage." Each asks the player to plan,
commit visibly, and execute cleanly. That's the roster identity you're after.
We only need to build the sequencer ONCE (for clones) to unlock all of them.
